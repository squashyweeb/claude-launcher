# 07 · Recovery — if a profile stops signing in or state goes missing

Rule 1: **don't delete anything**. Rename or move the suspect dir
first, then try to launch. Deleting is a one-way trip that loses state
(including local chat history, drafts, device registration) that
cannot be regenerated by re-login.

## Symptom: "Use your Claude API account" screen on launch

What it means: the webview can't find a valid `sessionKey` cookie for
`claude.ai`, so Claude Desktop drops to its login chooser.

Diagnostic flow:

### 1. Confirm it's a cookies / IndexedDB problem (not DPAPI)

```powershell
# Compare Local State against a known-good profile's Local State
fc /b "<broken profile>\Local State" "<good profile>\Local State"
```

If they match byte-for-byte, DPAPI/ABE is irrelevant and the problem
is missing data on disk, not decryption.

### 2. Inspect the Cookies DB

Sqlite install needed. On this machine the portable ClaudePortable does
not ship `sqlite3.exe`; use `winget install SQLite.SQLite` or any
other install.

```powershell
sqlite3.exe "<broken profile>\Network\Cookies" "SELECT host_key, name FROM cookies;"
```

Looking for: `sessionKey`, `sessionKeyV3`, `__Host-ant_trusted_device`.
If you only see `__cf_bm` and friends, the auth cookies never landed.

### 3. Inspect IndexedDB

```powershell
Get-ChildItem "<broken profile>\IndexedDB\https_claude.ai_0.indexeddb.leveldb"
```

Looking for: `*.ldb` files or `NNNNNN.log` files > 1 KB. If you only
have `CURRENT` and `MANIFEST-NNNNNN`, the DB is empty.

### 4. Decide the fix

| Local State matches | Cookies DB has auth | IndexedDB has data | Action |
|---|---|---|---|
| yes | yes | yes | Not a swap/data problem. Check network, DNS, VPN, antivirus. Launch with `--log-level=0 --enable-logging=stderr` and inspect output. |
| yes | no | no | The profile was captured empty (classic swapper bug). Only recovery is re-login into this profile dir — see §A. |
| no | — | — | Someone copied a `Local State` from another Windows user, or Chromium rotated the key. Decryption will fail. Only recovery is re-login — see §A. |

### §A — Re-login without losing identity

1. Fully quit every Claude.exe for this profile:
   ```powershell
   Get-CimInstance Win32_Process -Filter "Name='claude.exe'" |
     Where-Object { $_.CommandLine -like "*<profile path>*" } |
     ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
   ```
2. **Back up** the whole profile dir:
   ```powershell
   Copy-Item "<profile path>" "<profile path>.bak-$(Get-Date -F yyyyMMdd-HHmmss)" -Recurse
   ```
3. Launch:
   ```powershell
   Start-Process '<CLAUDE_EXE>' -ArgumentList '--user-data-dir="<profile path>"'
   ```
4. Sign in in the window that opens.
5. **Wait ~30 seconds** after the sidebar + chats appear. This gives
   Chromium time to flush cookies to the SQLite file and LevelDB time
   to compact the WAL into `.ldb` SSTs. Closing earlier can leave the
   next launch in the same empty state.
6. Quit via tray-icon Quit (not just the window X).
7. Verify §2–§3 again — cookies and IndexedDB should now be populated.

### §B — If the profile dir is wiped or missing

You lose local chat history and local drafts for that profile. The
server-side chats are unaffected and come back on re-login.

```powershell
New-Item -ItemType Directory "<profile path>"
Start-Process '<CLAUDE_EXE>' -ArgumentList '--user-data-dir="<profile path>"'
```

Sign in. Everything server-synced reappears.

## Symptom: `Claude.exe` won't launch at all

- Check `<CLAUDE_EXE>` still exists and is 240 MB+.
- Open Task Manager → Details → confirm no orphan `claude.exe` holding
  the single-instance lock from a previous crash. Kill it.
- Delete `<profile path>\Singleton*` files (they regenerate):
  ```powershell
  Get-ChildItem "<profile path>\Singleton*" | Remove-Item -Force
  ```
- Launch with `--log-level=0 --enable-logging=stderr 2>&1 | more`.

## Symptom: launcher.ps1 window is blank / errors on startup

- Run it in a visible console so you see errors:
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File .\launcher.ps1
  ```
- Common causes:
  - Edited `$PROFILES` with bad PowerShell syntax.
  - A profile `Dir` path contains a quote or backtick that broke
    `-ArgumentList`. Keep paths plain.
  - PresentationFramework not loaded — only happens on PowerShell 7+
    with no .NET Desktop runtime. Install the x64 Windows PowerShell
    7 "Framework-dependent (64-bit)" build with the Desktop runtime,
    or use `powershell.exe` (Windows PowerShell 5.1), which ships with
    Windows and has WPF out of the box.

## Shim stopped working after a ClaudePortable update

`--profile=NAME` suddenly creates no new profile dir, or launches with
default userData.

See [03-shim-internals.md](03-shim-internals.md) § "If ClaudePortable
updates". Restore `index.pre.js` from the backup you kept and relaunch.

If you did not keep a backup: there isn't a public source for the
shim. Hand-recreate from the text in that doc.

## Nothing works, I just want to start fresh

```powershell
# Back everything up first
Move-Item '%USERPROFILE%\AppData\Roaming\Claude'                      "$env:APPDATA\Claude.bak-$(Get-Date -F yyyyMMdd)"
Move-Item '%USERPROFILE%\AppData\Local\Claude-Data'                   "$env:LOCALAPPDATA\Claude-Data.bak-$(Get-Date -F yyyyMMdd)"
Move-Item '%USERPROFILE%\AppData\Local\Claude-Data-Profiles'          "$env:LOCALAPPDATA\Claude-Data-Profiles.bak-$(Get-Date -F yyyyMMdd)" -ErrorAction SilentlyContinue

# Launch fresh — this creates a brand new %APPDATA%\Claude
<CLAUDE_EXE>
```

You now have an empty, logged-out install. Everything previous is
preserved in the `.bak-YYYYMMDD` dirs and can be renamed back if you
change your mind.
